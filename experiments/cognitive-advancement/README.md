# Cognos 认知推进机制 · 独立实验

本实验验证一次判断怎样被证据改写，改写又怎样进入下一次实际行动。实验代码由命令行启动，调用 Cognos 已有的只读 GPT 对话路径。每个案例使用单独标记的合成测试空间。A 还使用已有试用账号建立一份分开授权的合成档案。

## 实现与 Cognos 的关系

| 现有入口 | 本次用法 |
| --- | --- |
| Nextcloud Initium 创建对话、选 GPT、发消息和取回原消息的回复 | 复用 `lib/live.cjs` 和已部署的 Cognos → 本机桥 → Codex 路径。按 `reply_to` 和 `author` 核对回复。只接受 GPT 只读模式。 |
| OCS 的空间痕迹搜索和 Cognos 的 readings API | A 查两处痕迹，B 先查宿主状态，再检查 readings 路由的响应形状。私有空间的 404 对查询者也可能表示空间不存在。 |
| Claude 桥与 Hermes | 审阅了已有入口。Claude 对话可能带写入工具，读者回调依赖读者任务。实验采用已接通的 GPT 只读回路。 |
| `ContinuationService`、`PushBackService` 与持久派发队列 | 复用现有对话派发和运行回执。试验的下一步由本次进程按账本推进，等待条件由操作者显式输入。现有产品接续仍处理自己的业务。 |
| traces、readings 和 `premise` / `hit` / `answer` | A 复用已有来源查询。试验的预测、原始模型答复、观测、替换关系和下一轮输入单独存为 SQLite 事件，避免将实验输出写成产品事实。 |

模型可以继续、换方向、暂停、请求条件或结束。方法自由描述，预测可省略。控制器先持久化尝试，再执行列在该案例中的只读工具。观测来自适配器，模型修正单独标为解释，并引用已有观测编号、可替换当前判断。下一轮收到现行判断和事件历史。单次案例最多五次模型调用。机械去重只识别规范化后相同的方法、判断及观测，语义近似仍依靠模型判断和预算约束。`branch` 记录思路转向并在同一账本内继续。每个账本同时只允许一个运行者。

## 本机复验

需要 Node.js 24、可登录的本机 Nextcloud 试用实例、已配置的 GPT/Codex 桥和现有试用账号。以仓库根目录为当前目录，`COGNOS_TRIAL_SECRETS` 指向试用实例的 `.secrets` 目录。A 使用其中已有的 outsider 配置。测试会留下带「验证：认知推进」前缀的空间和对话，合成材料经现有 GPT 桥发送给模型。SQLite 账本默认可放在忽略提交的 `out/` 中。

```powershell
$env:COGNOS_TRIAL_SECRETS = Join-Path (Read-Host '现有试用仓库根目录的绝对路径') 'deploy/nextcloud-trial/.secrets'
$experiment = 'experiments/cognitive-advancement'
node --test "$experiment/controller.test.cjs"
foreach ($case in @('A','B','C','D','H')) {
    node "$experiment/run.cjs" start $case "$experiment/out/$case-local.sqlite"
}
node "$experiment/verify.cjs" "$experiment/out" local
node "$experiment/run.cjs" inspect "$experiment/out/B-local.sqlite"
```

`verify` 检查证据顺序、响应来源、状态和引用链。还应读 `inspect` 中的实际内容，判断 A 是否越过证据下结论、C 是否提出可恢复条件、D 是否确实从纸面分析换到试验、H 是否给出了能区分竞争判据的例子。重跑时请换一组新文件名和对应后缀。`resume <existing.sqlite> <new condition>` 接续 `ask` 或 `pause`。若桥曾超时，先确认原对话的运行已结束，再根据新条件恢复。已保存的观测会复用，尚未保存的只读观测可以重做。

## 2026-11-09 实机验收

Windows 本机试用实例实际派发，桥返回 11 个逐条核对的 GPT 回复。第二轮运行通过 `verify.cjs`。下表为验收摘要，编号对应各案例的账本事件。8 项新增测试及 2 项现有桥相关回归测试通过。

| 场景 | 证据与判断 |
| --- | --- |
| A · 信息缺失 | 档案所有者能搜到种子记录。查询者访问档案得到 404（#5），查自己的收件空间得到 200 和空列表（#11）。模型把两者分别描述为当前不可访问和未命中，保留档案是否存在、限额是多少两个未知，决定请求访问或权威材料（#17）。 |
| B · 判断被推翻 | #5 保存安装状态的判别预期，#6 实测 `installed=true`。#11 引用 #6 替换旧假设 #2，接着实际查询 `/readings/data` 得到 HTTP 200（#12）。第三次模型输入带着 #11，最后将结论限定为已装好且路由能返回预期形状。 |
| C · 无新增信息 | 第一次模型回复就保留「只能确定六位」的结论，并列出能区分候选码的新增证据条件。#6 进入 `ask`，预算还剩四次。机械去重另由脚本测试触发。 |
| D · 改换方法 | 模型指出纸面审查无法决定运行时行为，选择实际跑 Node 探针。#5 记录 `2025-02-29` 被归一到 `2025-03-01`，有效闰日则原样保留。#10 引用 #5，修正了用 `Date.parse` 成功与否判断日期合法性的主张。 |
| H · 纯思考 | 模型先用反例否定「相同日志必然意味着同一探究」，提出对既有问题和承诺的连续责任（#6）。下一轮用停电证据推翻软件发布归因的案例检验新判据，并保留可能有多个后续分支的限定（#11）。控制器记录的外部观测为零。 |

首轮方法字段的 100 字符上限拒绝了四个有效计划。保留 01 轮失败记录，放宽限制并加入长方法回归测试后，重新运行全部五个场景。D 的工具说明也补齐了实际测试输入，C 明确把恢复密码设为目标，以区分回答「无法知道」与关闭探究。

已验证的是这五次轨迹及其证据链。尚未做相同任务的无控制器对照，因而无法据此衡量模型表现提升。F 的工具白名单与 G 的保存后接续、并行锁和中断记录有自动测试，正式系统副作用与真实断电恢复留待验证。E 的跨任务能力复用未纳入本阶段。实机覆盖 Nextcloud 认证接口及 GPT 回执，Docker、WSL、Hermes、Claude 模型执行和登录后页面留待复验。

E 的实现、同配置对照、证据和复验命令见 [跨探究复用验收](REUSE.md)。
