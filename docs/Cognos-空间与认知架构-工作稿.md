# Cognos 空间与认知架构工作稿

状态：工作中的架构材料，不是最终本体。更新：2026-10-08。

## 当前起点

Cognos 先做可实际使用的笔记与会话空间。用户把 Obsidian 笔记、GPT/Claude/Opus/Hermes 等会话和其他历史材料带入后，亲自使用、整理、连接和修改，再从真实使用中判断空间架构需要怎样改变。

不要先把三种空间做成三个固定菜单，也不要把所有历史全文拼成一份总提示。每个来源保留自己的身份、时间、参与者、边界和原文；整合通过来源、引用、关系、分歧和当前工作稿发生。

## 当前三个空间候选

这三者是当前的结构视角，不宣称已经是最终数据模型。

### 主体空间

回答：谁在参与、从什么位置看、具有什么能力、带着什么连续性进入？

可能涉及人、Agent、会话参与者、身份、关注、权限、行动和确认。主体自己决定关注什么、建立什么空间、何时让 Agent 进入。Agent 不在没有请求时自主推进；用户点击或使用 `@` 明确召唤时才进入当前工作。

### 对象 / 存在空间

回答：什么正在被谈论、被保存、被连接、被形成，以及它以什么状态出现？

可能涉及笔记、会话消息、文件、任务、决定、代码、结果、概念、关系、假设、冲突和未确认候选。同一材料可以在不同空间和视角中出现不同作用，但必须保留同一来源身份。

### 世界空间

回答：项目之外实际发生了什么，并怎样限制或改变项目内部的理解？

可能涉及真实人的行动、文件系统、Git、外部服务、浏览器、检索来源、程序结果、模型实际响应和用户反馈。世界发生进入 Cognos 时保留来源和观察边界；解释不能冒充世界事实。

## 当前工作原则

1. 空间由主体明确建立，不要求先填写固定类型或目标。
2. 建立空间本身就是一个有效行动；空间的具体性质在使用中形成。
3. 空间架构以后再推进，不先规定固定三空间产品结构。
4. 主体自己决定视角、关注、边界、参与者和是否让 Agent 进入。
5. Agent 只有在用户点击或 `@` 明确召唤时才主动参与；不做 always-on、自主心跳或无请求的后台推进。
6. 笔记、会话、项目对象和外部材料都可以进入工作，但不要求先决定它们属于哪一种本体。
7. 历史整合不是把来源压平成一份摘要，而是保留来源空间，并建立它们之间的引用、关系、冲突、继承和重新打开路径。
8. 认知架构的判断优先来自真实使用中的困难和新可能，不来自一次抽象讨论后立即增加模块。

## “创立空间”作为核心动作：当前假设

创立空间不等于新建文件夹、项目或空白聊天。它至少表达一个暂定承诺：

> 主体认为这里有一件值得继续面对的事，因此给它一个可返回的连续位置；但主体不必已经知道这件事属于什么类型、最后会变成什么。

空间创建时需要的不是完整定义，而是足以继续的起点。用户可以只给一段原文，或一个对象/经历/疑问；名称、当前关注、参与者、材料边界都允许逐步形成。未填写不是校验失败，而是当前尚未决定。

创建动作的重要后果与约束：

- **连续性**：有稳定身份和返回入口；下一次回来时能看到从哪里开始、后来发生了什么。
- **边界**：当前哪些来源、讨论、尝试与结果属于这里，哪些只是被引用；边界可以修订，旧来源不能被覆盖。
- **可见性**：这是个人、指定成员还是团队可见，必须让用户明确控制；“创建空间”不等于“公开给组织”。
- **参与者**：创建者决定邀请谁；Agent 不默认进场，只有显式选择/`@` 才获得当前空间输入。
- **可变性**：空间可以改名、改变关注、加减材料、暂停、分叉或结束；这些变化不应倒改原始来源。
- **承诺程度**：从一段尚不清楚的发生到正式项目/任务/决定，不应被创建表单强迫一次完成。

### 可尝试的最小创建流程

1. 用户从空白处、笔记/会话/项目对象或外部发生选择“创立空间”。
2. Cognos 保留起点及其来源；询问可选的“暂时怎么称呼 / 现在想继续什么”，允许跳过。
3. 用户选择个人或团队可见范围；默认不扩大已有材料的受众。
4. 用户可选参与者/Agent；默认不自动添加 Agent，也不自动启动对话。
5. 建成后首先呈现起点、当前材料、空间对话和最近变化；用户可继续写、连接材料、召唤 Agent，或暂时离开。

这些步骤是待验证的行为假设，不是最终字段表。关键验收问题是：用户能否从“我还说不清”开始，稍后回来继续，而不被迫选任务/项目/类型；同时不会误公开来源或把用户尚未确认的理解当成正式结论。

### 与当前原型的差距

现有 `/notes` 新建空间只要求标题，并把空间作为账号所有者私有；这是一个可用的个人笔记试验，不等于上述“从对象起点创立空间”的完整机制。当前没有从既有笔记/会话一键发起空间，也没有团队共享边界、空间生命周期/分叉、可返回的创立理由或“当前继续什么”入口。因此不能把“空间 CRUD 通过”说成“创立空间已经设计完成”。

### 当前探针后的修正：起点接续比空间字段更先

当前系统有三条分开的起点：

- `/notes`：空白创建个人空间，再加入来源笔记并在空间内对话；
- `Activity`：从项目发生开始一个持续活动，保存材料、尝试、Context、形成和结果；
- `Project`：承载团队成员、讨论和被确认返回的项目事实。

隔离探针实际确认：空白空间和带来源笔记可创建；项目发生可以进入 Activity；但当前没有“从个人笔记/会话进入 Activity”的入口。这个断点说明当前最先缺的不是更多 `Space` 字段，而是**起点如何进入持续展开**的语义。

因此暂不把 Activity 改名为空间，也不把 Notes 直接改造成 Activity。下一项应先验证一个窄动作：用户在一份笔记上选择“围绕此起点继续”，系统保留笔记原始来源，建立一段可暂停/继续的展开过程，并明确显示它与原笔记的关系。需要观察：这是否仍然是个人空间内的工作，何时需要项目/团队可见，Agent 是否只在明确召唤时进入，以及一次展开的结果是否应回到笔记、留在展开过程，还是经用户确认进入项目。

这个动作的验收不是“多了一个按钮”，而是：原笔记不被覆盖；第一次展开能回指原笔记；第二次进入能继续同一过程；用户修订原笔记后，系统能区分旧来源与当前版本；没有自动公开、自动创建任务/决定或把 Agent 输出冒充确认事实。

### 可推翻条件

若真实使用显示用户更自然地先建立稳定项目/类型再工作，或“先不定型”使回访、查找和协作更困难，则需缩小上述承诺解释；若用户多数只要临时草稿、不需要独立连续性，则“值得获得持续位置”也不是每个空间都成立。反过来，若用户反复从同一来源另开空间，说明空间创建需要更清楚的起点继承/分叉，而不是更多预设字段。

## 当前对话本身作为实践

本对话暂时作为一个认知工作空间，主题是“Cognos 的空间与认知架构”。

来源：

- 用户与 GPT/Claude/Opus 的历史会话；
- Obsidian 中的 Cognos 材料；
- 当前 Cognos 施工台账、行动思想、产品和模型文件；
- 用户在本轮对主体空间、对象/存在空间、世界空间的明确表达。

当前形成的内容：

- 先做笔记与会话空间，再迁入真实材料并实际使用；
- 主体空间、对象/存在空间、世界空间是重要候选结构；
- Agent 是被主体召唤的参与者，而不是自主后台循环；
- 空间的性质由主体建立和使用，而不是由系统先验强制分类；
- 需要整合许多会话和历史，但必须保持每个来源的独立边界。

仍未决定：

- 三个空间最终是三个稳定空间、同一空间的三种视图，还是其他关系；
- 空间之间的进入、引用、分叉、合并和返回规则；
- 什么情况下一个会话、笔记或对象需要形成新空间；
- Agent 能对空间做哪些直接修改，哪些修改必须确认；
- 地图是主要界面，还是空间的某种可视化投影。

## 第一阶段实践目标

先建设笔记与会话空间，使用户能够：

1. 导入一份笔记或一个会话，并保留原始来源；
2. 继续编辑、拆分、引用和连接材料；
3. 看见不同历史来源如何围绕一个问题相遇或冲突；
4. 明确建立一个工作空间，而不必先选择固定空间类型；
5. 在需要时点击或 `@` Agent，让它在当前空间中读取、整理、提出关系或执行明确动作；
6. 由用户决定哪些 Agent 变化被接受；
7. 通过实际使用记录下一次真正需要改变的结构。

第一阶段的验收不是“认知架构已经定义完成”，而是用户可以把自己的真实材料带入，并且使用一段时间后，能够具体指出：哪里找不到、哪里关系不够、哪里边界不对、哪里 Agent 应该介入、哪里当前结构反而妨碍了思考。

## 与现有 Cognos 的关系

现有 Organization、Project、Discussion、File、WorkItem、Decision、Activity、Context 和事件留痕继续作为当前工程现实。它们不自动等于最终的主体/对象/世界空间本体。

现有 Activity 可以作为当前试验中的一种活动机制，但不能用它提前替代完整空间架构。后续是否需要扩展、嵌入或重构 Activity，要由笔记与会话空间的真实使用决定。

## 重要边界

- 本稿是架构候选和实践记录，不是认知能力已经实现的证据。
- 软件测试证明工程行为，不证明认知作用。
- Agent 的整理、关系和解释必须保留来源、提出者、时间和确认状态。
- 不因出现“主体/对象/世界”三个词就立即新增三个数据库模块。
- 不因历史很多就把所有历史默认注入每次模型调用；当前空间的实际输入必须可见、可解释、可回看。
