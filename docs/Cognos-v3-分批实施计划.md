# Cognos v3 分批实施计划

这份计划是总计划的施工层。它不替代关于 Cognos 要造什么的研究判断，而是把每一批工程工作限制在可检查的关系上。任何一批都必须说明实际发生了什么、哪些仍然没有解释；如果实现需要新增认识论对象，应先停在研究决策处。

## 当前阶段判断

当前已经完成 A-D：

- Context Assembly 已从活动服务中分离，并保存每次模型调用的实际快照；
- 开放 Envelope、旧协议兼容、暂停、无操作 Move 和多 Formation 跨轮保留已经可运行；
- Runtime Profile 能记录请求模型、实际模型、推理强度和 fallback 信息；
- 两个隔离的 GPT-5.6 high 活动试用已经产生证据；
- 全量回归为 142 项通过。

这证明了第一条活动脊柱值得继续，但没有证明 Cognos 已经解释了主体、空间、长期能力或认识本身。下一批只处理真实运行中暴露的缺口。

## 工作流：研究判断如何进入施工

每一批按以下顺序进行：

1. **提出缺口**：用真实活动、日志或用户操作指出当前行为哪里不足。
2. **形成 Implementation Packet**：写明本批目标、允许改动、明确禁止、验收例子和回滚点。
3. **实现与测试**：先在隔离副本改动，保留原始发生记录、旧数据和未提交工作。
4. **真实试用**：至少跑一个能触发该缺口的活动，保存 Context、事件和真实结果。
5. **复核**：区分程序事实、模型表达、用户判断和我们的解释；必要时撤回本批抽象。
6. **同步实际项目**：只有回归与真实试用均可复核，才同步到实际项目，并在施工台账登记。

长篇研究对话只作为依据，不直接交给执行者自行综合。执行者收到的应是本批 Packet；遇到超出 Packet 的架构选择时暂停并回报。

## Packet E：Context Integrity

### 目标

让我们能够回答“这一轮模型实际看到了什么”，并区分材料目录、实际正文、模型形成、最近遭遇和被排除的历史。

### 实施内容

- E1：在 `active_materials` 中同时保存材料身份、版本、纳入原因和本轮实际正文；目录信息与正文不能混为一项。
- E2：保留 `excluded_history` 与组装原因；不把未纳入的历史偷偷塞回提示。
- E3：活动页显示快照摘要，按需查看实际渲染提示；默认不在页面一次性展开长提示。
- E4：检查快照和 run event 的关联；若无法同一事务保存，至少记录孤立快照并在诊断中可见。

### 验收

- 材料正文修改后，下一次 Context 的版本和正文一致；
- 只引用目录但未读取正文时，快照明确显示这一事实；
- 页面能从一次活动跳到对应快照，再查看实际提示；
- 快照哈希与实际提示一致；
- 旧活动和旧数据仍可读取。

### 不做

不做全局知识图谱、自动相关性检索或新的 Material/Lens/Space 对象。

## Packet F：Organization ↔ Activity

### 目标

让 Activity 能从真实组织环境启动，也能把结果明确地返回环境，同时保留“模型提议不等于项目事实”的边界。

### 实施内容

- F1：从项目消息、文件、工作项、决定和用户输入启动 Activity，并保留来源 occurrence、项目和参与者；
- F2：在 Activity 内显示来源环境，用户能重新读取原始来源；
- F3：支持明确的返回操作：创建草稿文件、发布项目消息、建立工作项事件或保存决定草案；
- F4：返回操作先进入待确认状态，只有明确执行后才写入组织事实；失败和取消也保存为结果。

### 验收

- 从一条真实项目消息启动活动后，Context 能看到来源原文和来源版本；
- 模型生成的文件或消息默认是草稿/提议，不自动成为项目事实；
- 用户确认后，项目环境出现明确事件，并能追溯到 Activity Move、Result 和 Context；
- 重试不会重复发布。

### 不做

不做自动项目管理、自动分派、自动发布或常驻 Agent 循环。

## Packet G：Runtime Boundary

### 目标

使 GPT-5.6 high 试用成为可复现的运行配置，同时不把 Activity 架构绑定在某一个提供商或中转站。

### 实施内容

- G1：保留 `RuntimeProfile` 作为唯一展示和记录边界；
- G2：把当前 OpenAI 兼容调用从历史 `DeepSeekRuntimeAdapter` 命名中逐步抽出通用适配层，保留旧入口兼容；
- G3：记录 requested model、actual model、endpoint、reasoning effort、fallback、错误分类和能力声明；
- G4：启动时显示连接状态，但永不把密钥写入仓库、Vault、Occurrence、Snapshot 或结果。

### 验收

- 同一个活动可以在隔离配置中复现请求模型和推理强度；
- 连接失败、降级、协议错误、超时和用户中断分别可见；
- 更换模型配置不改变 Activity 数据协议；
- 生产 `.env` 仍由用户控制，不因验收脚本改成 GPT-5.6。

### 不做

不把 GPT-5.6 写成 Cognos 的唯一模型，也不在本批比较回答质量排行榜。

## Packet H：三种活动回归

### 目标

检查同一个开放运行骨架是否能承载不同活动，而不是把每一种活动重新做成专用产品。

### 三个最小实例

1. **开放现实处境**：从“我不知道如何实现理想”开始，观察系统是否先展开主体空间和结果空间。
2. **学习/构造**：从真实数学材料开始，观察构造是否生成新材料并回到下一轮 Context。
3. **创作材料**：从几个未解释的片段开始，允许并置、续写或暂停，检查协议是否强迫创作先声明目标。

### 共同记录

- 起始材料及来源；
- 每轮 Context Snapshot；
- Formation 是否形成、是否并存；
- Move 是否实际执行；
- Encounter/Result 的事实内容；
- 结果何时再次被使用；
- 哪一步由模型完成，哪一步由程序、用户或外部世界完成。

### 决策门

只有在两个以上实例反复出现同一种作用，并且这作用不能由已有通用机制解释时，才提出新的持久结构。否则保留为活动材料或历史记录。

## Packet I：架构复核门

完成 E-H 后，单独写一份复核，不直接开发新功能。回答三条原则：

1. 世界中的差异通过什么接触方式成为系统可把握的差异？
2. 对象、问题、方向和方法是在什么活动中形成的，哪些步骤来自模型能力？
3. 过去的结果如何改变当前 Context、可用行动或形成方式？

复核还要列出：

- 已被程序承载的关系；
- 仍只是模型表达或人的解释；
- 真实活动暴露的反例；
- 下一轮值得研究的问题；
- 明确仍不能实现的概念。

在 I 完成前，不新增 Space、Subject、Lens、Judgment、长期 Memory 或自我修改模块。
