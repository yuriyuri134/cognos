# Cognos 全链路审计：意图 → 架构 → 功能 → 前端

日期：2026-10-11
范围：Nextcloud 35.0.1、Cognos app、Deck 1.19.0、Obsidian 导入边界、Activity/Hermes 链路
结论等级：审计发现，不等于产品验收通过。

## 总结判断

目标不是“个人 Notes + AI 聊天 + Deck 任务”，而是：

```text
Obsidian/会话/材料中的尚未成形之事
→ 保留原文与来源
→ 在项目中持续澄清、暂停、修订
→ 人明确确认后才进入任务/决定/协作事实
```

当前 Nextcloud 实际形成的是：

```text
个人材料
→ 私有 Activity 来源快照
→ Activity 聊天页
Deck 卡片
→ 私有 Activity 来源快照
```

因此当前是局部骨架，不是目标闭环。结构性风险是把 Cognos 缩成普通 Notes/任务管理器。

## 已证明

- Nextcloud 是最终产品底座；FastAPI 只是行为验证原型。
- Cognos 自建材料空间和材料表使用 Nextcloud 数据库及当前 Nextcloud UID，不读取 FastAPI SQLite。
- 材料保存 revision、content_hash、source_json；材料进入 Activity 时保存不可变正文快照；同一版本可复用，修订后可产生新快照。
- Deck 卡片可以按读取权限生成 `nextcloud_deck_card` Activity 快照。
- Activity 和 Hermes 消息有路由、表和前端结构。
- Hermes 提示词要求区分来源、候选建议和已确认事实。
- Deck/Cognos 任务协作已有大量局部 API、权限、历史、状态和失败恢复证据。
- Deck 创建 400 的已知根因是将非看板成员放进 assignee/users；Cognos 事务入口对此有回滚保护，原生 Deck 入口不自动获得该保证。

## 有结构但未证明

- 运行时曾出现 `needsDbUpgrade=true`/503；已执行 `occ upgrade` 后现场显示 `needsDbUpgrade=false`，但 Notes/Activity完整浏览器链仍需重跑。
- Hermes 真实容器到 API 的认证、响应、失败后刷新和重启持久化没有当前现场闭环证据。
- Activity 的“继续”接口只保存 run 输入；Activity 页面实际使用 chat 接口。两者语义未统一。
- Activity 消息在 Hermes 成功后才写入；模型失败时不能证明人的输入已保留，代码顺序与目标相反。
- Activity 主要按 `actor_uid` 隔离，是个人记录，不是已证明的项目共同活动。
- Deck→Activity 只做单向快照，没有双向回链、卡片生命周期同步、重复点击幂等。
- AI 输出虽被提示为候选，但没有候选/确认/阶段采用/否决等服务端状态模型。
- 前端有来源 JSON、聊天和错误文本，但不是用户可理解的来源卡片、状态机和恢复流程。
- `info.xml` 源码版本与历史 live 版本出现 0.11.3/0.11.2 不一致，必须以现场 `occ app:list` 收口。

## 未实现/直接缺口

1. Obsidian → Nextcloud 的真实产品导入：没有 importer、source URI、hash/revision、幂等重复导入、修订同步和 UI 可见来源链。
2. Nextcloud Files → Activity：没有 file ID、ETag/版本、Files 权限复核、文件回链。
3. “来源进入项目”：材料进入的是个人 Activity，没有项目选择、项目成员授权、共同可见范围或项目回流。
4. Activity 共享参与者和项目归属模型。
5. Activity 暂停、恢复、失败、待修订、完成等生命周期。
6. Activity 中候选→确认→采用/否决/被替代的持久化状态和人工确认路由。
7. Activity → 项目讨论/决定/Deck 任务的人工确认回流。
8. AI 失败时先保存用户输入、显示 pending/failed、提供安全重试的协议。
9. Activity → 原始材料/Deck 卡片的可操作来源回链和修订比较。
10. Talk 来源链、签名校验、房间成员和 Activity 映射。
11. 跨 Notes/Files/Deck/Activity 的统一权限矩阵和双账号浏览器验收。

## 当前前端误导

- Activity 空状态写“从笔记或 Deck 卡片详情页点击”，但实际产品文案使用“材料/任务”，概念不一致。
- Deck 文案“围绕此任务继续”让用户以为必须先有任务，反过来压缩了从未成形材料开始的入口。
- Activity 列表只有标题和创建时间，没有来源、版本、当前阶段、最近推进时间。
- Activity 详情展示原始 JSON，而不是可读来源摘要和“返回材料/打开卡片”。
- 没有暂停、修订、分支、确认、采用、否决动作。
- 消息加载失败只写 console；发送失败没有明确的保留输入/重试上一条动作。
- AI 消息没有“候选/待确认”可见标识、时间、来源依据或模型状态。
- Deck 原生历史、任务状态记录、Cognos Activity 的“活动”概念没有区分。

## 优先级施工顺序

### P0：先恢复正确运行证据与核心语义

1. 统一 live app/source version，执行并验证 `occ status`、`occ app:list`、schema。
2. 统一入口语言：从“围绕此任务继续”改成“围绕此材料/卡片上下文继续”；明确保存的是快照，不修改原对象；明确 AI 输出默认待确认。
3. Activity 详情增加可读来源卡片、返回来源、版本/快照边界；不要只展示 JSON。
4. 修复 AI 消息协议：先保存人的输入为 pending，再调用 Hermes；成功保存 assistant，失败保留 failed 输入并支持 request_id 幂等重试。

### P1：完成真正的核心闭环

1. Obsidian 最小导入切片：原始归档保留，目标材料保存 `source_uri/source_hash/source_revision/import_batch`，同版本幂等，修订产生新版本。
2. 材料进入 Activity 时选择项目并校验已有项目成员；Activity 保存 `project_id`、参与者、来源版本。
3. Activity 生命周期：进行中、已暂停、待修订、已完成；提供继续、暂停、基于新版本修订、创建分支。
4. Activity 中人工确认后创建/关联 Deck 任务或项目决定，并保留回链；不自动把 AI 输出写成事实。
5. 双账号真实验收：材料所有者、Deck 共享成员、非成员、撤销成员，覆盖 401/403/200、刷新、重启、移动端和失败恢复。

### P2：扩大来源和协作面

- Files 来源与版本。
- Deck 卡片来源生命周期同步和重复点击幂等。
- Talk 来源和回复回流。
- 项目统一时间线、搜索、来源失效/删除/恢复策略。

## 不应继续做的事

- 不应继续单独堆 Deck 任务功能，把局部 J07 进展当作 Cognos 主线完成。
- 不应把 Obsidian 只整理到 vault 就称为迁入项目。
- 不应把 Activity 能打开、HTTP 200、存在 Hermes service 或提示词写了“候选”当作 AI/认知闭环。
- 不应在没有来源权限、项目归属和人工确认之前，把材料或 AI 输出自动公开、自动变任务或自动成为项目事实。
