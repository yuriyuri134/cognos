# 理解-提议-结果-接续 v0：已实现规格

作者：pi。更新：2026-09-12。地位：按《给 pi agent 的执行交接与推进约束》第 14 节实现的软件工作名，不宣称穷尽认识形式。模型与人负责理解和提出活动；软件负责保留具体关联、执行已支持能力、呈现真实结果及可靠接续。

## 一条连续链

原材料 → 当前理解 S → 活动提议 Move → 实际执行及结果 E → 保持或修订理解 S′ → 下一次 Move。

界面（共同展开 · 材料与创作）自上而下呈现：当前理解（含版本与引用）→ 准备做什么（Move 的意图、提出者、依据的理解版本）→ 实际得到什么（逐条真实结果）→ 等待回答或继续。理解的历史随活动修订保留，旧版本可回看。

## 最小持久契约

- **当前理解（situation）**：活动状态中的 `situation`，自由文本（可为空、模糊或"尚不清楚"）+ 可选 `refs`（材料 ID、版本、片段、一句说明）。引用只是来源关联，必须真实存在，不自动证明解释正确。每次修订形成新活动修订；理解的版本就是它所在的修订号。
- **Move**：`activity_moves` 表。稳定 id、提出者、`basis_revision`（依据的理解版本）、`intent`（参与者的解释，不是客观因果）、`execution`（具体执行步骤）、状态与结果。创建幂等：同一 `request_id` 只创建一次，重试不重复执行。
- **结果**：存在 Move 的 `results` 中，逐条带状态与真实内容。模型生成（create）、程序计算（evaluate）、历史取材（acquire）、用户回答（user_answer）各带自己的来源与作者，不混为同一种外部事实。执行失败/冲突如实保留，后续步骤不再执行。
- **接续**：参与者面对真实结果后可以保持、修订理解、提出下一个 Move、询问用户或暂停。同一次回复先存理解再绑 Move，Move 绑定到实际生成的版本。

## 执行步骤

read / evaluate / change（含 set_situation）/ acquire 沿用活动组织初版；新增：

- `create`：把模型生成的真实内容保存为可改写材料，标记"模型生成 · 参与者"，不得伪造原始导入；
- `ask_user`：本批执行到此停止，问题交给用户，本轮模型运行结束。只有用户真实提交的回答才是结果，不得代答；
- 旧协议 `commands` 字段继续接受。

## 用户回答

`POST /api/activities/{id}/moves/{move_id}/answer`（幂等 request_id）。回答保存为 Move 结果后，服务让模型面对该回答继续一轮；模型可修订理解、提出新 Move 或暂停。

## 失败与恢复

- 请求幂等覆盖 Move 创建、结果保存与用户回答；重试返回同一次执行。
- 网络失败/进程中断：已保存结果保留；状态为 running 但不在当前服务的 run 显示为 interrupted，不自动重放。
- 理解修订失败（如引用不存在）不毁掉整轮：错误留在事件里，Move 绑定当前版本。
- 预算到达保留当前状态与待续位置，不标为认识完成。

## 尚未实现（如实报告，不伪造）

语义检索、自动发现关键依赖、充分的世界探索、跨活动长期发展、外部行动统一展开（仍走既有 Handoff/DSH 链）。三类真实活动验收（复杂处境/数学学习/创作）尚未以真实模型完成；脚本替身已验证协议，两者证据分开。
