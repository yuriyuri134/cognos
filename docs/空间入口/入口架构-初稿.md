## 一、今天的入口是什么样的〔查〕

现在有两个世界，各有一个入口。

**开发 Cognos 的 agent**（Claude Code、这些线程、Codex、Hermes CLI）：
- 入口是会被自动塞进上下文的那几个文件：`CLAUDE.md`（现在用 `@` 导入 PROJECT-OVERVIEW）、项目记忆的 `MEMORY.md`、各家的全局文件。
- 这是手工的、静态的版本〔AI 转述，`怎么让它不偏.md`〕。

**产品里的 agent**（Hermes，在创立空间、Activity 里被叫出来时）：
- `HermesAgentService.php` 第 582 行，创立空间里，它进来时拿到的是：
  > 「你是 Cognos 的 Hermes Agent，专注于帮助用户探索和深化认识……你的角色是：提出深入的问题……提供多角度的观点和候选理解……不要简单给答案，而是引导用户自己发现」
- 第 950 行，Activity 里：
  > 「你是 Cognos 中被用户明确召唤的参与者……只把回答作为候选理解、提议或待验证问题」
  
  后面跟着标题和材料正文。
- `ActivityContextAssemblyService` 拼出来的上下文，栏目是固定的：formations、tensions、moves、affordances。这些是 9 月 FastAPI 原型的词。

〔AI 70%〕这几处说的都是「你是谁、该怎么表现」，没有说「你在哪、这里有什么、以前有谁试过什么、停在哪里」。

- 「提供多角度的……候选理解」和 9/7 的否决直接冲突。
- 「引导用户自己发现」和你 10/24 那句也在拉扯：「难道不应该是学会自己先回答、深入问题吗？？」

所以产品里已经有一个入口，只是它给的是角色，不是位置。下面的架构要替换的就是它〔AI 65%〕。

## 二、入口是什么

**入口是主体和空间相遇的地方。空间在这里，从这个主体站的位置，把自己显出来。**〔AI 55%〕

这里有三个依据：
- 〔原 2026-06-23〕「空间也是视角下的观点，是可切割划分的，作用在于强调空间内的观察」
- 〔原 10/24〕「但是这同样取决于视角」
- 〔原 2026-06-05〕「所以主体在哪归主体在哪，地图有多大和世界有多广阔是世界的事情」

推下来的三点〔AI 55%〕：
1. **入口不是一页固定的说明。** 同一个空间，你进来、Hermes 被叫进来、本地 Claude Code 进来，显出来的不一样。不一样的原因是三样：谁、带着什么、站在哪。
2. **入口要把两样分开显：主体站在哪，和空间有多大。** 显出来的永远只是一部分，入口要让进来的主体知道还有它没看到的。这就是你 10/7 说的〔原 2026-10-07 Hermes〕「类似于地图那种感觉」「它意味着可能性，以及存在以及结构的视角下的边界」。所以地图上要标边界，也要标空白。
3. **入口也是出口。** 主体走的时候，它的尝试留在空间里，下一个进来的人看得到。〔原 10/24〕「从历史中不断复盘，和对于未来的不断预测和尝试，是双向构建的」。我的读法是：进来的时候经过历史，走的时候留给历史，中间是这一次尝试〔AI 50%〕。

**入口和总指导是一对**〔AI 60%〕：
- 总指导六问，是主体问自己的；
- 入口，是空间能拿出来回答这些问题的东西。
- 空间答不出的地方，入口照实显成空白，不编。比如还没人试过，或者意图还说不清。

## 三、空间要拿得出什么：对着六问

这些不是栏目，也不是步骤。它们是「主体问到这里时，空间里有没有东西能回答」〔AI 55%〕。

| 主体问自己的 | 空间要拿得出的 | 依据 |
|---|---|---|
| 1. 我在哪？谁让我来？还有谁在？走后留下什么？ | 这个空间在哪些更大的空间里面，那些空间为了什么；这次是谁叫的、原话是什么；别的主体在不在，最近做了什么；这里会留下什么 | 〔原 2026-08-18 pi〕「应该围绕着每个成员都做上架构 设计才是，比如右侧的项目参与者点击进去，是属于他的主体空间」 |
| 2. 这里有什么？哪些以为用不了，其实能申请？ | 这里的材料；进来的主体自己的可能范围（工具、权限、记忆，能申请的） | 〔原 2026-06-06〕「空间，依托于存在或者说主体的可能范围」；10/24「Vault 读不到」那次错 |
| 3. 对象、意图、为了什么？ | 意图用原话放，标是谁的、什么时候说的、在做什么（定义、类比、举例、提问、顺口一提）；不止一个意图就分开放；说不清的就照「说不清」放 | 〔原 2026-05-26〕「往往对于结果集合是模糊的」；盈利循环第 5 条 |
| 4. 以前想过吗？ | 以前的尝试，各自停在哪里；纠正；否决；没解决的张力 | 〔原 2026-09-14 pi〕「之前讨论的思考的部分都去哪里了？」 |
| 5. 刚才有什么值得记？ | 一个能留下痕迹的地方。留下的东西标来源，读法和发生分开放 | 读法引擎；记录与经过-机制 |
| 6. 是不是重要部分？ | 哪些地方被说过要单独拎出来做 | 〔原 10/24 22:24〕 |

第 1 行里「更大的空间」，是我觉得最容易被漏掉的一样〔AI 65%〕。读法引擎那一轮就是这么偏的：它站在一个窄的空间（「读小林」）里，没人提醒它这个空间在「三个空间内的东西怎么展开和生长」里面。Hermes 被叫进一个 Activity，也只看见这个 Activity。

## 四、几个架构上的决定（都是我的，等你看）

### 1. 空间里放的是「发生」和「读法」，入口显的是读法，但每条都能回到发生〔AI 60%〕

- **发生**：原话、现实碰回来的反馈、某个主体做过的尝试。发生了就不改。
- **读法**：某个主体对发生的理解，例如「我读这句是在说……」，标是谁读的、有几分把握。
- 两个主体的读法可以不一样，各自留着。〔原 10/24〕「他的尝试也可能和我是不一样的，甚至方向相差甚远，但也是一种」。
- 一种读法被反复撞到矛盾时，换切法。这是读法引擎证明过能用的那一条；这次用在空间上，不是用在你一个人身上。

这也部分回答了张力 5（记录会不会冻结尝试）〔AI 40%〕：发生不改，冻住的只是某一种读法，而读法可以换。尝试本身还是会被记录改变，这一点我没有回答。〔原 2026-07-06〕「我们在定义或者记录尝试的时候，和尝试本身，或者我想要达到的效果是不一样的」。

### 2. 每条信息要带上「它是一个什么样的存在」〔AI 55%〕

一条信息至少带这几样：
- 谁的：原话、现实、哪个 AI；
- 什么时候；
- 它当时在做什么：定义、类比、举例、提问、顺口一提；
- 把握多少，只有 AI 的才标；
- 状态：确认、只是说过、被否；
- 它和哪个意图、哪个对象有关。可以「无关」，也可以「不知道」。

这就是〔原 10/24〕「理解和认识每个信息甚至是存在」落到一条信息上的样子。

**这里有一个和否决表的张力，我要明说**〔AI 45%〕：它看起来像一套固定 schema，而 8/12 已经否了「固定 Space/EntityObject/Relation 模型」。我的区分是：
- 8/12 否的，是给世界规定好有哪些东西、东西之间有哪些关系；
- 这里只给每条痕迹标「来路」，不规定空间里有什么。

但这个区分站不站得住，我只有一半把握。

### 3. 不是关卡〔AI 70%〕

10/20 你删掉了「点进去先建空间」。入口不能要求进来的主体先做任何事：不填表，不先建空间，不先选一个模式。
- 对你，它可能几乎看不见：一个侧栏，或者页面顶上一两行。
- 对 agent，它是被放进上下文的东西，不是一份「请先阅读」。

### 4. 回来的时候，不默认「接着上次」〔AI 60%〕

- 〔原 2026-06-28〕「我回来往往也不是继续，而是沿着这个大方向，但不是最后的位置，是另个位置」
- 盈利循环那次你也说「看情况」〔查，以尝试为核心 v1 第六节之二第 7 条〕。

成熟产品几乎都默认「回到你上次停的地方」。这里入口要显的是三样：大方向（意图）；上次停的几个位置；你走以后，对象自己变了什么。站到哪里，由进来的主体决定，系统不替它选。

最后一样来自〔原 10/19〕「一方面是在认识对象，一方面对象本身也在生长、突破和变化」。所以入口要显「你上次之后，这里长了什么」，包括别的主体做的。

### 5. 主体自己的视角，进来时也写出来，并且留下〔AI 55%〕

进来本身就是一次尝试：试着弄清自己在哪。〔原 2026-06-26〕「视角其实是在寻找主体」。

所以 agent 进来以后，先写两三行再动手：
- 我站在哪；
- 我读到的意图是什么，经过了哪几条；
- 这一步是不是因为好做才选的。

这几行跟着它的尝试一起留在空间里。这就是 `怎么让它不偏.md` 第二层说的「让回答看得见」。只是它不再是一份流程，而是入口的另一半：空间显给主体，主体也把自己显给空间。

偏了，你或下一个主体当场就看得到。如果 10/24 05:16 那张选择题前面有这几行，可能当场就会被看出来〔AI 50%〕。

### 6. 空间属于项目，入口属于空间；agent 只带着自己的可能范围进来〔AI 65%，接 10/25 那段〕

- 项目里可以有许多空间，切法可以不同〔原 10/25〕。「创立/示范」是一种切法，「主体/对象/世界」是另一种。
- 每个空间都有入口，用的是同一套机制。
- 空间可以套在空间里。从里层进来，入口要把外层的意图也显一点（第三节第 1 行）。

### 7. 先放在产品里，开发这边的文件是它的手工版，也是第一批材料〔AI 50%〕

- 在开发这边（Claude Code、线程），能「放进」agent 上下文的只有自动加载的那几个文件。入口在这里只能是文件，所以那几个文件要短，指向全集。现在就是这么做的。
- 在产品里，Cognos 自己决定 Hermes 进来时拿到什么。`ActivityContextAssemblyService` 和那几段系统提示，就是入口该在的位置。所以真正会动的入口，应该做在产品里。
- 两边可以接上：把「Cognos 这个项目」本身，当成示范空间「项目」部分里的第一个项目。这些材料（思想总索引、否决表、各线程的纠正、这两天的偏移记录）就是第一批填进去的东西。
- 接上以后，开发这边的 agent 也从这个入口进来。`怎么让它不偏.md` 说「让 agent 不偏」是 Cognos 大问题的一个实例，接上以后，两边就真的是同一件事了。

## 六、不是什么

- 不是给你小林这个人建一个画像。读法引擎已经走过那条路，它的对象太窄。
- 不是固定的「主体 / 对象 / 世界」三个栏目〔原 10/1 笔记〕。三空间「只是沟通用简化，不是本体」。
- 不是一张候选菜单，也不是先填后进的表单。
- 不是流程。六问是问题，入口是空间对这些问题拿得出的东西，两边都不规定顺序。
- 不是一个会自己醒来的东西，不做自主心跳。主体进来时，入口才显出来。

## 七、我最担心的：它是不是又收窄了〔AI 60%〕

入口只是空间被碰到的那一面。你 10/24 08:34 说三个空间要做的是「建模，填充……映射，和构造……可以作为一种模拟」。这些入口都没有碰到：
- 入口能显出「这里有什么」，但它不会让空间生长；
- 它也不会在模型上模拟一次尝试。

如果只做入口，很可能会做成「一个很好的上下文组装器」。那就是把「全新的映射建模方式」收窄成了「agent 进门时读什么」。

我还是认为应该先做它，理由是：
1. 每个主体都要经过它；
2. 它逼着空间先回答「你里面有什么」，这会马上暴露出空间缺了什么样的填充，也就是第二个方向要做的事；
3. 现在产品里的入口是错的，它在给角色，不给位置，而且在主动违反 9/7 的否决。

但这个判断只有 55%。
