# 接入一条路：任何 agent 怎样进项目做事

[总纲](../README.md) · [接入与能力核验](接入与能力核验.md) · [共同工作怎样发生](../02-协作/共同工作怎样发生.md) · [阶段与验证](../04-交付/阶段与验证.md)

2026-11-03。小林：「是不应该只有一个agent，不一定是hermes，我不确定他值不值得」。所以这里不绑哪一家：本机 Claude Code、Codex、Hermes 或以后别的，走的都是同一条路。能接 MCP 的用 `tools/cognos-space-mcp/server.py` 的工具；不能接的直接调下面的接口，效果一样。

## 四步

| 步 | MCP 工具 | 接口（OCS，`/ocs/v2.php/apps/cognos/api/v1.0`） | 留下什么 |
|---|---|---|---|
| 1. 进来 | `enter_space` | `GET /spaces/creation/{id}/enter?subject=<名字>` | 入口文字。项目位置的入口最前面是对这一处适用的在生效的决定（没有就照实写一句），然后是谁在动什么、这一处的当前内容和材料。 |
| 2. 登记在动什么 | `start_work` | `POST /spaces/creation/{id}/runs` `{subject, purpose}` | 一次运行（`cognos_runs`），状态 running，输入快照是此刻的入口；入口里给了哪几条决定记在 `cognos_run_decisions`。项目页「谁在动什么」里出现它的名字。 |
| 3. 做事时报依据（可不报） | `note_basis` | `POST /spaces/creation/{id}/basis` `{subject, decision_quote | revision, note}` | 依据记在这次运行上（`cognos_run_dependencies`）。决定用原话里的一段来指，不用编号。 |
| 4. 交回 | `check_changes`、`hand_back` | `GET /runs/{run_id}/drift`，然后 `POST /spaces/creation/{id}/messages` `{subject, run_id, result_id, content, depends_on?, acknowledged_drift?}` | 结果进这一处的讨论；同一个 result_id 只收一次。交回时记下起步以后才有、输入里没有的决定，和它报过的依据有没有被改成更新的版本；看过差异再交回的，记下看到的时间。结果照收，不自动用到共享内容。 |

`hand_back` 在起步以后有了它没看到的决定、或它依据的内容被改了时，第一次调用不交，先把差异给它看；它看完（可以改自己的结果）再带 `acknowledged=true` 交回。这就是 V12 里「依据被改的那一位在交回前看到差异」。

身份：调用用的是用户给这个 agent 建的 Nextcloud 应用密码，`subject` 是 agent 自己报的名字。交回的署名必须和登记的那次运行一致，不一致不收。agent 不能用用户自己的名字登记。

## 经桥的那一位

本机 Claude Code 经 `claude_bridge.py` 被 Cognos 叫起来时，第 1、2、4 步由 Cognos 和桥代做：Cognos 先记运行再叫桥，入口直接给它，桥做完替它交回。它自己只用第 3 步，以及交出去时允许的 `write_content`。两种方式在页面上看起来一样，都是「谁在动什么」里的一位。

## 叫不醒、看不到的

网页上的会话 Cognos 叫不醒，也看不到它读没读过。页面上对它固定写「尚无证据」，并给一段可复制的入口文字（适用的决定原话 + 这一处现状）。复制过去以后它仍是「尚无证据」，直到它自己走上面这条路进来。

## 2026-11-04：交回重试与差异版本

MCP 的 hand_back 发送前把 result_id、原结果和确认过的差异摘要存到本机。网络或回执丢失后，用同一运行和原结果再调用，会重发同一编号；进程重启也可恢复。结果尚未确认时不能用新文字覆盖它。成功回执保留，后续相同调用直接返回已交回。不重做实际工作。

状态目录由 COGNOS_MCP_STATE_DIR 指定，默认用户目录的 .local/state/cognos-mcp；按服务地址、账号、主体、空间和运行隔离，使用操作系统文件锁防止同时交回。文件包含结果正文，不含密码，不上传仓库；未确认的记录不要清理。当前不提供后台自动重投，重新调用 hand_back 才重试。

GET /runs/{id}/drift 返回 drift_token，绑定本次具体差异。MCP 只有在相同差异已展示后才接受 acknowledged；期间又变化会先展示新差异。直接调接口交回时，同时传 acknowledged_drift 和对应 drift_token。旧确认或仅传 true 时，成果仍保存，但不记为看过当前差异。摘要不是权限凭据，也不证明模型理解或采用。

以上为 0.28.1 当时边界；后续已将结果、委托数据库收尾原子提交，并落位持久接续和派发队列。外部进程动作未知与运行级 fencing 仍未完整验证，不能把客户端可重试等同于全部外部动作已恢复。


## 2026-11-04：Codex 实际接入与工作读取（0.32.1）

同一条运行/差异/交回路径已由本机 Codex 实际走过，不新增 Codex 专用项目模型。`tools/cognos-space-mcp/codex_entry.py` 每次限定一个位置，只配置本次连接的工具，不改全局配置；独立应用凭据、文件只读和工具列表限制见工具目录 README。主体仍是自报名字，账号权限仍来自该 Nextcloud 账号，不把进程名或配置存在当成强身份认证。

工作工具 `list_work_items/get_work_item/preview_work_split` 走 `/spaces/creation/{id}/work-items`、`/{workId}`、`/{workId}/split/preview`。工作有原作者与版本，读取/预览不改变这些记录；跨位置和外账号请求拒绝。入口的工作摘要进入实际输入快照，上限 10 份并报告省略和截断。

`check_codex_entry.py` 真实记录 Codex 六个入口/工作工具调用、登记和第 2 版依据；中途新增决定，再由真实 Claude Code 改成第 3 版；第二次独立 Codex 调用沿原 run_id 查看新决定与实际行差异并交回。`check_codex_receipt.php` 核对输入、决定时间、差异确认与唯一消息回执。页面显示 Codex 起步后才有的新决定为交回前看到，Claude 为进入输入，网页端仍为尚无证据。`check_codex_retry.py` 再开真实 Codex 复用原成功回执，无新运行或重复消息。两段 Codex 调用之间有停顿，不以此证明两个模型始终同时生成。

限定位置的差异检查与交回现在共用同一状态键；成功回执在服务暂时离线时也能从本机确认。未限定位置时，`check_changes` 按声明只传 run_id 也可取得正确上下文。边界测试连同原有回流故障检查共 17 项通过。

0.33.0 已接上 AI 在明确委托下修改/拆分工作并记录实际作者，见下节。仍需接 Cognos 自动叫起 Codex 和网页会话。


## 2026-11-05：单份工作维护授权（0.33.0）

经桥委托可以独立授予 `may_manage_work`，必须关联具体工作；默认没有。`update_work_item/split_work_item` 使用原委托运行，不重新 `start_work`。改稿、采用和工作维护是三个分别授予的权限。真实 Claude 已通过这条路修改工作交付、读取新版、预览并确认拆分；子项留作未指派工作，作者记 Claude Code，原结果仍在父委托。当前独立 Codex 入口默认工具列表仍只允许读/预览工作；没有默认扩大其写能力。

工作维护遇新决定或已报依据变化也先展示并确认对应差异。稳定操作编号用于网络重试，成功后复用原回执；完成或拆分后的重复请求仍能取回回执，但不能据此开始新操作。实际运行已交回、失联或项目/工作安排改变后拒绝新修改。授权与作者细节见[工作项与拆分](工作项与拆分.md)。
