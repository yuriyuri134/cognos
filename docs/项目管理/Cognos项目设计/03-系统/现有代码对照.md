## 现有服务怎么接

### SpaceService（发生和读法）

留着，当每个位置自己的只增不改的记录。它已经做到：发生不改、改状态靠 `correction` 新写一条、每种 kind 写入时各自检查（hit 必须指向 premise，answer 必须指向 hit……）。

要改的是键：现在一片空间是 `(space_type, space_id)`，实际只有 `creation`。加一种 `location`，位置建好后它的发生就记在 `('location', <位置 id>)` 下。已有的两片创立空间不搬数据，在位置上记一个映射（`legacy_space = 'creation:2'`），读位置时把它下面映射的旧空间的发生一起读出来。

### SpaceEntryService（入口）

这是设计里「每次进入先看到什么」的现成地方：人看到的侧栏「这里」和被叫进来的 agent 拿到的系统提示是同一份（`entry()` + `renderText()`）。

- 现在 `resolve()` 只认创立空间，归属只看创立空间的主人。要加位置和项目，并按授权判断谁能进。
- V12 要求「在生效的决定」和「谁正在动什么」排在入口最前面。决定从 adoptions 里读（范围含这个项目、还在生效的）；「谁在动什么」从 runs 里读（状态是领取或运行中的）。
- 「从你上次来以后，新的是什么」已经有：`space_seen` 按主体记上次来的时间（`markSeen`/`lastSeen`）。它只能说明某位参与者「进来过」，说明不了「读到了这条决定」或「照着它改了」。新决定对每一位走到哪一步（存下、送到、读到、照着做）要另记：读到看那次运行的输入快照里有没有它，照着做看交回的 depends_on（见[共同工作怎样发生](../02-协作/共同工作怎样发生.md)五）。`space_seen` 留着当「上次来以后有什么新的」用。

### ContinuationService（没完的事、接着走）

它做的是设计里「运行机会 → 运行 → 停在哪 → 下一次」的一个最小版本，只服务一个端（本机 Claude Code）。对照：

| 现在 | 设计 | 怎么接 |
|---|---|---|
| `open` 发生：挂着没完的一件 | 运行挂接的目标之一（没形成任务也能接着走） | open 继续能用，不改成工作项。它后来被确立成工作项时，两者互相连上，open 不收。 |
| `stop` 发生：接着 / 卡住 / 完了，加口子 `stopped_at` | 运行结束时的结果和下一步，等待和结束分开表达 | 对得上。 |
| `resume()`：先接刚才那件，再按挂上的先后（id 小的先） | 先筛出能跑的，再由负责的参与者判断做哪件，记下「为什么现在做它」 | 筛选留在服务里；挑哪件交给被叫起来的那位，入口里把所有还拉着的列出来，让它在 `stop_here` 里写为什么选这件。 |
| 当天次数、下一次从哪条分支接着：存在 app 配置里 | 预算和继续条件记在委托和运行上 | 搬到 runs / grants 里。 |
| 口子和以前的几乎一样（字二元组重合 ≥ 0.6）就记「原地」，这一件停下 | 文字相似只用来提醒复核，不当成判断 | 对不上，见第 6 条。 |
| 桥忙就不叫，等手上那件做完、结果发回来时再接着叫 | 排队、领取、租约 | 发回失败时这个「再接着叫」也一起丢了，见桥一节。 |

### PushBackService（叫回来）

反对和回应已经是设计里 challenge 的样子。要改的两处：

- 排队存在 app 配置里一个 JSON 列表（`pushback_queue_<类型>_<id>`），里面是 `hit:<id>` 或 `msg:<id>`。改成表里的待处理项，和运行机会放在一起，这样项目页上看得见排着什么。
- 能叫回来的人是写死的两个名字（`Claude Code`、`Cognos`）。改成看参与者有没有能接的运行端（participants + grants）。

### Activity

Activity 是另一条早一些的线：从卡片或笔记开一个活动，带当时的来源快照，选一个 Hermes 参与者对话。现在本机库里 0 行。

代码里有两套没接上的东西：`ActivityRunService::executeContinue` 会建运行、组上下文（`ActivityContextAssemblyService`）、存快照，但没有任何地方调用它。页面上的「接着」走的是 `ActivityController::continueActivity` → `chat()` → `HermesAgentService::chat`，这条路不写 runs、也不存快照。所以 `activity_runs` 和 `activity_context_snapshots` 一直是空的。

建议：Activity 不当项目的骨架。它的来源快照（`source_snapshot`）和上下文快照的字段，拿来当 input_snapshot 的样子；它的消息表在 conversation 上登记成另一种 provider。`executeContinue` 要么接上要么删，不要留着让人以为运行已经有记录。这件事不在首版必做里，但要在对照里写清楚，免得有人按类名以为已经有了。

### Deck 卡片

Cognos 已经在 Deck 上做了一层可靠的任务操作：创建带幂等（`task_requests`），每次改动记一条（`task_events`），改名、指派、状态都有接口和检查脚本（`deploy/nextcloud-trial/check_task_*`）。这些都留着。

- 首页「项目」不再链到 Deck，链到新的项目页。
- 项目和看板的关系：一个项目可以挂一个或几个 Deck 看板（新表 `cognos_project_boards`），工作项可选连一张卡片。
- `list_projects` 工具改成返回 Cognos 项目，Deck 看板另给一个工具。

### 桥（`tools/cognos-space-mcp/claude_bridge.py`）

现在的一次运行：

1. Nextcloud `ClaudeBridgeService::send` POST 到桥，带系统提示、消息、`open_id`、`reply_to`、`hit_id`。桥收下回 202，在本机起一个线程跑 `claude`。
2. 同一片空间同时只做一件：桥进程里的一个集合 `BUSY`。桥一重启就没了。
3. 做完调 `post_back`，POST 到 OCS `/api/v1.0/spaces/{type}/{id}/messages`。失败时只写一行 `回答发不回 Cognos：…`，结果就丢了。本机日志里已经有一次真实的：`HTTP Error 503`（10/28 那次升级后 Nextcloud 要求升级数据库）。
4. Nextcloud 收到后 `SpaceApiController::addMessage` 存消息、清掉「还在做」的标记、调 `ContinuationService::afterRun`，再调 `PushBackService::drain` 和 `resume` 叫下一件。这里不去重：同一个结果发两次，就会存两条消息，也会再叫一次下一件。

对上设计，按先后：

1. **Nextcloud 先建运行，再叫桥。** `send` 之前在 `cognos_runs` 写一行（run_id、挂接目标：工作项、open、尝试或会话，输入快照、状态 queued），把 run_id 带给桥。页面上「谁在动什么」读这张表，不再读 app 配置里的时间戳。
2. **桥把要发回的结果先存下来。** 本机写一个待发送目录（每个结果一个文件，带 result_id 和 run_id），发成功再删。桥起来时先把没发出去的重发一遍。运行目录 `record_run` 已经存了输入和原始输出，可以放在同一处。
3. **收结果按 result_id 去重。** `addMessage` 收到已经收过的 result_id 就回原来的结果，不再存消息、不再叫下一件。
4. **领取和租约先做最简单的。** 现在只有一个桥，`BUSY` 换成运行表上的状态和租约到期时间就够了；多个端时再加 token。
5. **桥自报的名字要核。** 桥用一个应用密码账号（默认 `cognos-admin`）发回，写进去的作者是请求里自报的 `subject`。设计要求作者由可信会话定。先做到：只接受这次运行登记过的参与者名字。

做完 1 到 3，V08 里「结果已存但投递失败、再投只生效一次」就能测；也修掉了实施说明里点名要先修的那一处。

## 要的迁移

现在库里 app 版本是 0.18.2。11/03 我把本机从身体分支切回 master 时，身体分支用过 0.19.0（多了 `cognos_space_traces.judgment` 这一列，可以空，master 不用它），重新启用 app 后记录的版本回到了 0.18.2。下一次 master 加迁移，版本号用 **0.20.0**，免得和身体分支的 0.19.0 混在一起；新迁移照现在的写法先查 `hasTable`/`hasColumn`。

建议的几步，每一步一个 PR，旧表都不改、不删：

| 步 | 新表 | 旧数据怎么挂进来 |
|---|---|---|
| 1 项目的底子 | `cognos_projects`、`cognos_locations`、`cognos_location_history`、`cognos_project_boards` | 不自动建项目。小林在项目页上建项目时，可以把一片创立空间、一个 Deck 看板挂进来，写一条映射。 |
| 2 决定和谁在动什么 | `cognos_adoptions`、`cognos_grants`；participants 加 Claude Code | [判断采用与纠正](../02-协作/判断采用与纠正.md)里已经列的那几条决定，由小林确认后作为第一批写进去，不从 traces 里自动推。 |
| 3 运行一定回得来 | `cognos_runs`、`cognos_run_inputs`、`cognos_results`（result_id 唯一） | 之前的运行没有记录，不补造；桥本机运行目录里有的，可以登记成「旧运行，只有原始记录」。 |

## 设计和代码对不上的地方

按重要程度排。每条写了建议改代码还是改设计；改设计的几条，我没有直接动对应文件，等小林看过再改。

1. **结果会丢，而且丢了没人知道。** 设计要求运行持久、结果待发送、同一结果只生效一次；代码里运行只在桥的内存里，发回失败只写日志，收的那边不去重。本机已经发生过一次（503）。改代码，排第一（见桥一节）。
2. **设计的「位置」和代码的「空间」是两套说法。** 代码里所有能力（发生、入口、接着走、叫回来）都挂在 `(space_type, space_id)` 上。建议改设计：在[数据模型](数据模型.md)里写明，位置在发生这一层就是一种空间，它的发生、读法、入口沿用现有的那套。这样首版不用把这几块服务重写一遍。
3. **项目根本不存在，首页的「项目」是 Deck。** 设计没问题，改代码（迁移第 1 步）。要注意的是 Hermes 的 `list_projects` 现在返回 Deck 看板，项目建起来后要跟着改，否则 agent 看到的「项目」和页面上的不是同一种东西。
4. **「在生效的决定」没有地方放。** 小林的话进来是一条普通的 `intent` 发生，和别的发生排在一起；入口里没有单独一块。V12 直接依赖它。改代码（迁移第 2 步 + 入口最前面一块）。
5. **设计说想法、采用分表，不要用通用节点表；代码里想法、反对、回应、没完的、停、检查、更正都在一张 traces 表里。** traces 不是没有约束的节点表：每种 kind 写入时有自己的检查，只增不改。建议改设计：首版承认 traces 是想法和反对的版本记录（每条 premise 链就是一个 claim 的各个版本），采用另开表；等真的需要按想法查「谁依据了它」时，再从 traces 投影出 claim 表。这条要小林定，因为它决定第 5 步之前要不要先重构 traces。
6. **「原地」靠文字相似就把一件事停下。** 代码里两个口子的字重合到 0.6，就记一条「原地」并停下这件；设计（D08）说文字相似只供复核。建议改代码：记一条提醒，但这件还拉着，由下一次被叫起来的那位看了再说。改之前要先看 10/27–28 观察记录里「原地」实际拦下过什么，这条我还没核。
7. **会话有三条入口，各走各的。** 创立空间的对话（`HermesAgentService::chatCreation`，叫 Claude Code 时走桥）、Activity 的对话（`HermesAgentService::chat`，只走 Hermes）、MCP/OCS 的空间接口（`SpaceApiController`）。设计要人、内嵌模型、外部端调同一套业务服务。建议：项目的对话建在创立空间那条线上（入口、发生、桥都在这条线上），Activity 先不接进项目。
8. **Activity 的运行记录看起来有，其实一直是空的。** `ActivityRunService` 和上下文组装都写好了，没人调用。不阻塞首版，但实现边界里「Activity 有相关类」那句要改成「有类，没接上」，免得被当成已有能力。
9. **参与者和授权。** Claude Code 不在参与者表里，能做什么由桥的环境变量决定，作者名字是自报的。首版至少要把 Claude Code 登记成参与者，桥只接受登记过的名字。
10. **笔记的版本分两处存。** 当前版本在 `cognos_notes`，旧版本在 `cognos_note_revisions`。用作来源版本时两处都要读，固定引用某个版本时要能找到当前行之外的版本。不用改设计，实现时注意。
