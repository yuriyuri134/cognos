# 工作项、委托与拆分

2026-11-04，app 0.32.0，草稿 PR #42。承接[对象关系](../01-产品/产品与对象.md)、[重组](../01-产品/开始与重组.md)和[共同工作](../02-协作/共同工作怎样发生.md)。

## 工作有自己的身份

`cognos_work_items` 保存明确工作的范围、负责人、交付、验收、状态、完成依据及版本；除范围外可以后补。当前位置 ID 是主归属，项目从位置查得，因此独立、合并和撤回后同一个工作仍可找回，不另搬一份工作。`cognos_work_events` 同事务保存每版原记录、操作者、说明和时间。

自由探索的 `open` 发生继续按原对象使用，不迁成工作项。委托和运行也保留自己的身份。一份工作可以有多次明确委托；结果收到不自动把工作标成完成。负责人是用户填写的安排，不推定被写到的人已接受承诺。完成要留下交付或验收依据，重新开展要留原因；这些是参与者的记录，不是系统证明成果已经正确。

## 拆分实际改变什么

先给 2～12 份各自的范围，可分别写负责人、交付与验收。预览说明原工作的版本、保留的原委托和结果，以及旧资格失效。确认校验工作版本、当前位置与项目运行代际，和历史一起原子提交；输入改变后要重新预览，同请求重放返回同一批子项。

原工作变为「已拆分」，不是「完成」，保留原说明与经过。每个子项用 `split_from_id` 和 `split_from_revision` 指向拆分前的具体一版，自己的初版记录同时留存。子项未填的负责人、交付、验收保持未填，旧委托与权限不复制，也不会自动派发。原工作作为来路保留，后续改各子项。

## 委托和资格

工作页的「安排这份工作给 AI」只填好已有委托表单；明确提交时才登记关联，当前稿修改和采用授权默认不勾选。委托保存 `work_item_id` 与 `work_epoch`，并留下工作版本事件；没关联工作的旧委托继续使用原有规则与请求重放签名。

同一项目锁下串行处理改范围、拆分和新委托登记。工作范围、负责人、交付或验收改变，以及等待、完成、取消和再开会更新工作资格；原委托的直接改稿、采用和再次准入同时校验项目与工作资格。「待开展」和「进行中」之间单纯标记进度不撤回现有资格。

拆分不证明外部进程已停止。先前已派出的运行仍可能交回或产生外部动作，不能因拆分盲目重跑。迟到结果留在原位置，原工作与委托的联系不被改写；没有当前资格的成果可留作比较或提议。子项需要自己的安排。外部操作的完整 fencing 和停止核验仍在可靠运行的未完成范围。

## 页面和接口

位置页支持登记、修改、记录完成依据、查看版本、拆分预览和分别安排；项目总览可查看各位置的工作。刷新遇到未保存输入时保留表单，版本冲突时先展示新版并由用户比较。增添或修改拆分内容会清掉旧确认预览。

接口沿用登录、版本、请求幂等和事务规则：

- `GET /projects/{projectId}/work-items?location_id=...`、`GET /projects/work/{workId}`。
- `POST /projects/locations/{locationId}/work-items` 登记，`PUT /projects/work/{workId}` 更新安排与状态。
- `POST /projects/work/{workId}/split/preview` 和 `/split` 预览与确认。
- 现有委托接口可附 `work_item_id`、`expected_work_revision`，须在同一位置。

工作读取和拆分预览已在 0.32.1 接到 MCP；0.33.0 已接上明确单份委托授权的 AI 工作写入，见下节。工作依赖、跨尝试服务关系、Deck 执行视图也尚未接；旧委托的事后归入工作入口也尚未提供。它们继续在原规划里，不以当前拆分页面代替完整 P1/P2。

## 已有证据

`check_work_items.cjs` 实际 8780 身份、版本、拆分来源、幂等、完成依据与重组后身份检查；`check_work_split_permissions.php` 实际数据库检查旧写入/采用/准入拒绝和迟到结果保留；`check_work_concurrency.php/cjs` 四组独立进程交错检查。`check_work_items_live.cjs` 实际 Claude 接下工作关联委托、一次回流、未自动完成及拆分不重派；登录浏览器检查真实表单、冲突输入、两份预览后添加第三份使预览失效、三份确认、完成依据、真实结果展示和 390px 界面。原有真实委托内采用及页面也已回归。


### 代理读取与预览补记（0.32.1）

`SpaceApiController` 为代理提供按位置读取工作、查看原版本和拆分预览。入口含未完工作摘要，省略和截断如实报告。`check_agent_work_read.cjs` 核对独立 Codex 应用凭据、外账号/错位置拒绝、预览不改作者版本、12 份工作时只给 10 份摘要并标 2 份省略。实际 Codex 已调用这些工具，未真实拆分原工作；工程与页面证据见[接入一条路](接入一条路.md)。0.33.0 的 AI 直接维护绑定明确委托范围并记录实际 AI 作者；应用密码与网页用户写接口本身不能表达这层业务授权。


### 明确委托内维护工作（0.33.0）

关联一份工作后，用户可以另行勾选「可以维护关联工作的安排」。默认不勾，未关联工作时不能勾；与改当前稿、采用权限分别记录，旧委托不会因此得到新权限。AI 可以在这一份工作里改范围、负责人、交付、验收，记录状态和完成依据，或预览后确认拆分；不会自动取得别的工作或子项的权限。

代理写入口校验实际运行、署名、账号、位置、关联委托及 `may_manage_work`，同时校验租约、项目和工作代际。AI 自己在允许范围内修改后，仅本次委托跟随这份工作的新代际；人或其他参与者改变范围会使旧资格失效。完成、取消、等待或拆分不续权。结果交回与工作修改在项目锁下串行，已交回的运行不能继续写；迟到结果仍可保存，不把撤回资格解释成外部进程已停止。

新决定或已报依据变化时，工具先给出新决定和实际行差异；只有确认匹配这次差异的 `drift_token` 才写入。保存过的操作通过稳定请求编号取回原回执，确认标记变化不会使同一次操作多写一版。原用户接口请求签名保持兼容。

版本经过分别保留账号、实际 AI 主体、运行、委托和确认过的差异指纹；子项记录实际 AI 创建者，原委托和结果仍在父工作，子项不继承也不自动派发。代理接口新增 `PUT /spaces/creation/{id}/work-items/{workId}`、`POST .../{workId}/split`；MCP 为 `update_work_item/split_work_item`，运行编号由桥附加。自由登记的运行不能充当维护授权。应用密码仍属于对应账号，这层业务检查不替代后续多账号或细粒度凭据隔离。

`check_work_management.php` 为真实数据库权限与幂等检查；`check_work_management_api.py` 为真实 HTTP 的拒绝、差异确认和回执丢失重试；`check_work_management_live.cjs` 为真实 Claude 修改交付、预览并确认拆分，子项未启动且当前稿未改。并发与登录页面证据见阶段记录。
