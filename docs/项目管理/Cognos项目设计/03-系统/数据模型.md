# 数据模型与存储责任

[总纲](../README.md) · [产品对象](../01-产品/产品与对象.md) · [接口](接口与一致性.md) · [实现边界](Cognos依赖与实现边界.md)

## 模型的地位

这是支持本组操作的逻辑模型，字段名是候选契约，不是现有 Nextcloud 表结构，也不是对 Cognos 一切存在的建模。采用关系型元数据、文件/既有来源存储及派生视图作为首版起点；全文索引后续可加，语义索引不成为保存和接续的前提。（经过 S07 §15–17、S09、D01/D02）

存储责任分开：原始来源保存实际取得内容；运行日志保存调用和回执；应用修订保存组织及采用的变化；当前状态是由已提交修订获得的可查投影。旧 JSONL 和 runtime 状态继续由原组件负责，新表不静默成为旧历史的替代真相。（S09；技能历史数据边界）

## 首版怎样落库

下表列的是逻辑职责，不是必须逐项新建的表。也不以“压成 6～7 张表”为目标：按事务、查询和历史需要拆分。原文消息继续复用已有会话表；判断、挑战和阶段性记录先复用发生/版本内容；用途保留独立关系；正式采用与用户决定有独立行为，不藏进自由文本。

用户决定用轻量 decision 记录：id、scope、content（用户原话）、source_message_id、original_author、recorded_by、status(active/revoked)、superseded_by、revision、created_at。AI 代录不改原作者；范围和替代变更留历史。缺原文时只能保存候选解释，不能伪造用户决定。

当前共同工作内容以位置为入口，记录 content、revision、editor、可选来源消息及旧版本。它可以引用多个方案，不以覆盖原话的方式“整理”。AI 结果接入当前稿需保留来源关系；正式采用状态另记。原文和修订不能只剩当前快照。

首段物理映射：projects/locations/location_revisions/usages；每个位置关联一个独立的既有 creation 对话，复用已实现的运行/结果表。这个对话只是过渡适配，不把 project、location 和来源会话合成一种实体。未来 conversation 独立化时保留映射和旧链接。decision/adoption/grant 在后续业务操作落地时各自迁移，不预建空表假装能力完成。

## 核心记录

所有稳定对象使用不可变 ID；可变对象带 revision、创建/修改者及时间，修订记录含依据和理由。时间保存发生时间与系统取得时间，界面按用户时区呈现；来源未知的时间不补造。

| 记录 | 主要候选字段 | 关键约束 |
|---|---|---|
| project | id, title, description_revision, root_location_id, status | 根位置唯一；名字和路径不作身份。 |
| location | id, current_project_id, kind, parent_id, title, revision | 主导航父项至多一个、同项目且无环；项目根无父项。 |
| location_history | location_id, project_id, parent_id, valid_from/to, change_id | 重组保留当时归属；旧链接可回溯。 |
| attempt | id, introduction_revision, initiator, focus, state | 简介与阶段总结不同；可关联多个位置。 |
| stage_summary | id, attempt_id, content_revision, covered_refs | 作者、阶段范围及旧版本可读。 |
| work_item | id, description, owner, deliverable, acceptance, state | 依赖及服务对象另关联；完成需交付依据。 |
| conversation | id, provider, external_id, runtime_binding | 来源内稳定 ID 去重，模型名称不等于会话身份。 |
| message | id, conversation_id, external_node_id, parent_id, author, source_revision_id | 保留分叉；转贴者与原作者分开。 |
| source/source_revision | id, provider_id, external_id, version, content_ref, hash, acquired_at, coverage | 原件与摘要身份不同；hash 检查内容，不自动证明作者。 |
| usage | id, target_id, source_object_id, selector, purpose, version_policy, permission_scope | 多对多使用，选区与用途独立；读取时记录实际版本。 |
| claim/claim_revision | id, author, content, basis_refs, status | 方案/判断/挑战为有作者内容，不与采用合表。首版沿用现有只增不改的发生表（想法、反对、回应都在里面），不拆开；只把采用另开一张表（11/03 小林「可以」，见现有代码对照）。 |
| adoption | id, scope_ids, claim_revision_id, adopted_by, authority_ref, state, supersedes | 固定采用版本，作用域逐项校验；旧记录保留。 |
| challenge/impact | id, target_revision, basis_refs, responder, state; impact_target | 纠正指向版本；影响目标按关系去重，不自动撤销全部引用。 |
| participant/grant | id, kind, bindings; scope, operations, limits, expiry, revision | 身份与运行绑定分开；当前授权可撤回。 |
| change_set | id, actor, authority_ref, expected_revisions, reason, basis_refs, operations, committed_at | 成功变化不可覆盖；当前投影与变化同事务。 |
| run/input_snapshot | id, target_type, target_id, purpose, trigger_id, grant_revision, state, lease_token; object_versions, source_manifest | 挂在会话、尝试、位置、工作项或 Initium 条目上，work_id 只在挂工作项时有；起步位置不可改写，改挂新增关系并核新目标权限。起步依据固定，后续读取追加；运行状态可变且有状态变更日志。（[共同工作怎样发生](../02-协作/共同工作怎样发生.md) 二） |
| run_dependency | run_id, object_id, object_revision, level | 记录上报或业务操作明确使用的依据、版本及取得方式；未上报不等于没有依赖。当前约束由系统另行检查，不依赖上报完整。（同上 三） |
| change_reach | change_id, participant_id, event(saved/delivered/included/responded/applied/verified), evidence_ref | 记录可观察证据；输入包含不等于理解或采用，未取得回执为未知，不断言谁不知道。（同上 五） |
| operation/result/verification | operation_id, idempotency_key, receipt; result_id, artifacts; verifier, criteria, outcome | 执行声明、实际结果、验证和采用分别表达。 |
| outbox/delivery_receipt | event_id, target, payload_ref, retries; result_id, receiver_ack | 可靠交回，重投递不重执行。 |

对象关系可使用带明确类型及端点约束的 relation 表补充，如 formed_from、serves、depends_on、supersedes、split_from；usage、adoption 等有独立行为的关系仍用专用记录。不要用没有约束的通用节点表隐藏所有产品契约。

## 版本与关系实例

示例数据是候选演示，没有创建真实项目。

```text
conversation C17 / message M42 / source_revision SR3
usage U1: target=L项目形成, source=M42, purpose=确立入口依据, pin=SR3
usage U2: target=L模型回复, source=C17, selector=M12..M20, purpose=分析回复环节
claim K5@2: 首版包含基础重组，作者=AI甲，依据=M42、旧方案差异
adoption A6: scope=L项目设计, claim=K5@2, adopted_by=有权参与者
run R9: target=W3(work_item), input=K5@2+A6@1+SR3, depends_on=K5@2, result=Z9
```

甲位置撤回 A6，不改 U2；K5 更新到版本3，不改变 R9 的输入。C17 加新消息形成来源新版本，U1 的固定依据仍在，其他跟随用途得到更新线索。

## 生命周期、权限与一致性

移动位置保持 ID；独立为项目时可让原位置成为新项目根，将原所属写入 location_history。合并时源 project 标合并，原根转为目标下的位置或映射到目标位置；每项采用/工作/权限的处理以预览方案为准。

位置的导航归属不决定来源访问权；读取需要参与者权限、来源权限及用途约束都满足。关联、独立和合并不扩大访问。公开元数据也要检查，以免标题和引用摘要泄露不可读材料。

关系删除通常停用而非抹掉历史；正常文档维护使用修订。确需处理来源撤回或删除时，访问和删除策略由原来源及明确授权决定，留下可允许保留的失效标记，不宣称“原文保留”可以越过实际删除要求。

## 投影、搜索与备份

当前项目页、时间线、待面对项和搜索是派生视图，带投影版本或更新时间。搜索返回索引版本与可回原文路径；索引落后时不把它当当前事实。可以重建投影，但必须保留原材料引用、修订、采用和回执，不能只备份当前表。

跨文件存储先写入并校验内容，再在事务中登记引用；事务失败时未引用文件可按保留期清理。备份恢复要核来源 hash、对象版本、投影进度、待投递结果与授权状态；恢复演练见 V11。实际采用全快照还是差量及文件大小限制，按 Q07 的数据量核对选择。
