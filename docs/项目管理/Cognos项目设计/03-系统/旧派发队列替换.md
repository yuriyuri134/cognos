# 旧派发队列替换：实现切面

2026-11-04 核对基线 2c031f9。状态：持久存储基础已实现，实际派发入口仍未切换；不是额外常驻模型提示词。

## 为什么需要替换

PushBackService::drain 先把队首从 IConfig 的 JSON 数组移除，再调用 AI。读取、修改、保存不原子；两个 busy 请求可能相互覆盖。hit 在 drain 内调用，msg 返回给 FollowupDispatcher 后调用；只改 msg 会漏掉反对叫回。call 把未知错误也压成 called=false，drain 可能跳到下一件。现有 Followup 意图保护一次接续选择，但还没有把选中的工作与实际运行绑定起来。

这次核对还确认桥对重复 run_id 没有独立回执缓存：按 space busy 拒绝，空闲后同 run_id 可再次执行。因此不能靠重发同一 HTTP 请求实现 exactly-once。

## 目标行为与接口

持久队列项保留 space、kind(msg/hit)、原 message/trace ID、入队顺序、领取意图 ID、派发 run_id、状态和经过。引用原内容，不复制另一份 AI 摘要。排队和实际运行是两种事实。

状态 queued→claimed→sent，明确忙拒绝可回 queued；领取后失联或派发结果未知为 unknown，失效的原目标为 skipped。sent 只说明已派出，不代表结果完成。未知项不能自动回 queued。新条目/显式重新委托另记尝试，不覆盖旧记录；相同待处理原因不重复排队。

先把旧数组按原顺序导入，新表中记录原条目的稳定导入身份；保留旧值作为迁移证据。重复导入不复活已完成项。前插队列的用户消息仍前插，已有 hit/msg 都继续工作。创建新记录、选队首、领取和状态迁移走数据库事务，不再用缓存数组当事实源。

FollowupDispatcher 只领取工作，不持事务等网络；领取记录需与当前 followup 和新 run 一起建立明确关系。桥发出前先存 run；run_id 回写队列项必须在同一数据库事务中，而非拿到 202 才回写。这样“已经可能开工，但队列还不知道是哪次运行”的窗口才会缩小。

PushBack 的 immediate hit、busy hit、busy msg，以及手动 recall 都要经过同一个排队/派发入口。保留现有是否叫回主体、预算、原目标是否已回答等判断，但将“跳过无效项”与“未知派发”区分；未知不继续取下一项。用户再叫一次应是明确的新尝试，不能被稳定消息 ID 永久去重，也不能让网络重试重复生成尝试。

## 必须验证的实际行为

- 两个并发 enqueue 不丢记录；重复 pending 原因只有一项，显式新尝试有独立历史。
- 两个领取者只有一个取得同一项；同空间未知项阻挡后续自动派发。
- msg 与 hit 均覆盖：明确 busy 不丢原项；已开始但响应丢失不重放；原目标失效可跳过而不伪造完成。
- 旧整数 hit 与字符串 msg 数组导入顺序不变，重复导入不复活已发送记录。
- 领取后、创建运行后、HTTP 后、结果后分别注入故障，核队列/运行/结果关系。
- 真实桥忙时用户写一句，原话一次入队、恢复后仅有一次实际回应；暂停及恢复不悄悄续旧授权。

## 运行结果同步（0.30.2）

RunService 的接受/失败/未知迁移和队列更新放在同一事务；接收结果时，队列收尾也进入原结果事务。accepted 对应 sent，失联/响应不明对应 unknown，迟到结果将自身绑定恢复为 sent；sent 仍只说明派出/结果已接收，不伪称工作判断正确。租约到期逐项走相同条件迁移，不只批改运行而漏队列。

仅桥明确 BUSY 的失败可将原队列工作重排为 queued，清当前 run/followup 资格；旧失败 run 的不可变 input_snapshot 仍保留原队列领取关联。其他明确拒绝为 skipped，避免无效请求无限循环。更新必须匹配当前 run_id，旧回执不能覆盖后来新 run 的绑定。通用 settle 只处理未绑定运行的队列项，不能绕过运行事实回排。
